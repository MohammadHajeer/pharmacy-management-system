# Project AI Instructions

`AGENTS.md` is the source of truth for project-wide AI coding rules. Read it before making changes, then read `docs/DEVELOPMENT_GUIDE.md` and any documentation relevant to the assigned feature.

## Project stack

- Django
- Django Templates
- Django Forms and ModelForms
- Django ORM
- Django built-in authentication
- Django Groups and Permissions
- Tailwind CSS v4
- Vanilla JavaScript
- `uv` for Python dependencies
- `npm` for frontend tooling

## Do not introduce

Do not add any of the following unless explicitly approved:

- Django REST Framework
- React
- Vue
- Angular
- HTMX
- Alpine.js
- Bootstrap or another CSS framework
- Another authentication system
- Unnecessary dependencies

Use the existing Django, Tailwind, and vanilla JavaScript architecture.

## Project structure

- Feature apps: `apps/`
- Shared project templates: `templates/`
- Shared layouts: `templates/layouts/`
- Reusable components: `templates/components/`
- Shared JavaScript: `static/js/`
- Feature templates: `apps/<feature>/templates/<feature>/`

Keep feature-specific models, forms, views, URLs, templates, and tests inside the owning app. Register new apps in `config/settings.py` and include their URLconfs from `config/urls.py` only when the assigned task requires it.

## Templates

- Use `{% extends %}` for layout inheritance and `{% include %}` for reusable components.
- Dashboard feature pages should normally extend `{% extends "layouts/dashboard.html" %}`.
- Authentication pages should extend `{% extends "layouts/auth.html" %}`.
- Do not duplicate the sidebar, topbar, or shared components in feature templates.
- Review `docs/COMPONENTS.md` before adding or changing shared UI patterns.

## Navigation

- Sidebar configuration lives in `config/navigation.py`.
- Navigation processing lives in `config/context_processors.py`.
- Do not hardcode duplicate navigation lists in feature templates or views.
- Preserve namespace-based active states, group visibility, unavailable-link handling, and future permission handling.
- Use namespaced URL names such as `medicines:index`.

## Authentication

Use Django's built-in users, sessions, groups, and permissions.

Current groups, whose names must remain exact, are:

- Owner / Admin
- Pharmacist
- Inventory Manager
- Accountant

Do not create a custom `Role` model or a new authentication system unless explicitly requested.

## Authorization and permissions

Hiding a sidebar link is not authorization. Every protected view must enforce access with Django authentication and permissions. Prefer model permissions and `permission_required`/`PermissionRequiredMixin` once feature models exist. Keep group membership as a way to assign permissions and control navigation visibility, not as the only security boundary.

## Tailwind CSS

- Use the existing theme tokens defined in `assets/css/input.css`; do not introduce random colors.
- Use complete, static class names so Tailwind can detect them. Do not construct classes dynamically, such as `bg-{{ color }}-500`.
- Do not edit `static/css/output.css`; it is generated by the Tailwind build and ignored by Git.

## JavaScript

- Use minimal vanilla JavaScript.
- Avoid large inline scripts in templates.
- Put shared behavior in `static/js/` and load it through the shared template structure.

## Models and database

- Do not create or modify models outside the assigned task.
- Follow the agreed business requirements document (BRD) and entity-relationship diagram (ERD).
- Generate migrations with Django and review them; do not manually edit migrations unless necessary.
- Keep business queries and relationships within the owning feature app unless a documented cross-app boundary requires otherwise.

## Dependencies

Do not install a dependency unless it is necessary for the assigned task. Explain why any new dependency is required and use `uv` for Python packages or `npm` for frontend tooling as appropriate.

## Scope and collaboration

Only change files needed for the assigned task. Do not refactor unrelated code, delete another developer's work, or implement future features without a request. Preserve unrelated working-tree changes and coordinate changes to shared files with the relevant feature owners.

## Validation

Before finishing, run the checks relevant to the change. Typical commands are:

```bash
uv run manage.py check
uv run manage.py test
npm run build:css
```

Add or update focused tests for changed behavior. Report any check that was not run and why.

## Git

Do not commit, push, merge, or rebase unless explicitly requested.

At the end of a task, report:

- Files created
- Files modified
- Important decisions
- Checks and tests run
- Things intentionally not implemented
- A suggested commit message
